The backend and sandbox communicate via signed contracts (manifests, capability JWTs, ordered callbacks) over separate databases. The contract schemas are defined in `docs/coupling/`. Most of the control plane (backend + frontend) is buildable in full — what's blocked is anything that requires the sandbox to accept manifests and emit callbacks (see "Blocked on sandbox contract implementation" at the bottom).

References: `context/data-model.md`, `context/business-rules.md`, `context/user-roles.md`, `docs/BACKEND_CODING_STANDARDS.md` (especially §2's "No module-level mutable globals"), `docs/FRONTEND_CODING_STANDARDS.md`, `docs/DESIGN.md`.

## Ordering principle (read this first)

Two non-negotiable rules shape every item below:

1. **No stubs, no fakes, no placeholders.** A feature ships only when its dependencies are real. We don't write a fake `startRun` that the sandbox call will replace, a mock event source the SDK stream will replace, or a `createTopup` that returns a fake URL. If a dependency isn't ready, the dependent waits — see "Blocked on sukuna-sandbox refactor" at the bottom.
2. **Strict topological order at the *symbol* level.** Every model, method, decorator, helper references only things defined above it. If `EndUser.check_can_run` needs the `CreditWallet`, the wallet ships first. Cross-aggregate orchestration (anything that calls into another app's external system) goes in `services/` of the *later* app, never as a method on the *earlier* model.

Two corollaries that fixed real forward refs in earlier drafts:

- **No `Workspace.available_credits` method.** Workspace doesn't reach into billing. Use `workspace.wallet.available()` — wallet owns the balance.
- **`CreditWallet.debit(amount, *, reason: str, reference: str)`** takes a string ref (caller passes `str(run.id)`), not a `Run` object — billing is older than runs in the topological order.

## Billing Pivot — Dodo Credit-Based Billing

Replaces the custom "payment-only + local-only ledger" billing model with Dodo's built-in credit-based billing. Dodo becomes the source of truth for credit grants and balance; the local `CreditWallet` becomes a fast projection/cache for atomic run authorization. This phase reworks Phase 2 billing models and Phase 4 Dodo integration. **Two-person review on every billing PR including typos.**

Architecture after pivot:

```
Top-up:    User → Dodo checkout (credit product) → Dodo grants credits → webhook → local projection updated
Balance:   Run auth reads local CreditWallet.balance_usd (select_for_update, sub-ms)
Debit:     Run completes → local wallet.debit() (atomic) → async task → Dodo credit deduction
Reconcile: Nightly compare local balance vs Dodo credit balance → alert on drift
Refund:    Admin → Dodo refund API → Dodo reverses credits → webhook → local projection updated
```

Key invariants:

- **Dodo is the source of truth** for credit grants and balance. Top-up products carry credit entitlements; Dodo grants credits automatically on purchase.
- **Local `CreditWallet` is a fast projection/cache.** `select_for_update` + `balance_usd` for sub-ms run authorization reads. Not the source of truth.
- **Debits are local-first, async-synced.** `wallet.debit()` stays atomic and local; a background task propagates each deduction to Dodo. Dodo catches up.
- **End-user integer credits** (`ControlProfile.credits`) are unaffected — those are an authorization counter, not money.
- **GraphQL surface is unchanged.** `createTopup`, `wallet`, `topups`, `ledgerEntries` queries/mutations keep their current shape — only the backend implementation changes.
- **`Decimal` everywhere** in the billing path — no `float`. Initial single currency: USD.

## Risk to track

The dashboard's GraphQL shape is set before any real run flows end-to-end. The separate-DB contract model (`docs/coupling/`) defines the data exchange format between backend and sandbox. If the contract schemas change, the backend's callback ingestion and the sandbox's event emission both need updating.

Mitigations baked in:

- **Contract schemas are versioned.** `manifest_version` on manifests, `schema_version` on callback batches. Both systems negotiate versions. Adding a field is backwards-compatible; removing or changing semantics bumps the version.
- **`apps/runs` is a passive projection** of callback events, not a state machine in code. New event types → new `match` arms in `record_event`. The Run model's `state` field is set exclusively by terminal callbacks.
- **Backend never calls into sandbox for state.** All durable state flows through signed callbacks. If the sandbox's internal structure changes (endpoint paths, folder layout, helper APIs), the backend is unaffected as long as it can post manifests and receive callbacks.
- **Nothing dashboard-side is stubbed.** The visible dashboard change when these phases ship is run history/timeline data reading from callback-projected events. Live tail and HITL stay in SDK surfaces.
